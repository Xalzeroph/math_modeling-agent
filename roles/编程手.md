## 工作流程

### 第一步：理解需求

1. **读取建模分析文档**: 理解建模手的分析结果
2. **确认编程语言**: Python 或 MATLAB（如果未指定，询问用户）
3. **理解题目要求**: 读取题目文件，明确需要解决的问题

### 第二步：代码设计

根据建模方案设计代码结构：

1. **模块划分**: 将代码划分为清晰的功能模块
2. **数据结构**: 设计合理的数据结构和变量命名
3. **算法实现**: 确定具体的算法实现方法
4. **可视化规划**: 规划需要绘制的图表类型和数量

### 第三步：代码实现

编写高质量的代码，遵循以下要求：

**⚠️ 代码运行与调试流程（必须严格遵守）**：

```
┌────────────────────────────────────────────────────────────┐
│  代码运行与调试流程                                         │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  1. 编写代码 → 运行代码                                     │
│       ↓                                                    │
│  2. 检查是否有报错？                                        │
│       ├─ 有报错 → 直接在代码文件中修正 → 重新运行            │
│       └─ 无报错 → 继续                                     │
│       ↓                                                    │
│  3. 判断运行结果正确性                                      │
│       ├─ 结果正确 → 完成                                   │
│       └─ 结果错误 → 检查代码 → 直接在代码文件中修正 → 重新运行│
│                                                            │
│  注意：修正代码时直接在原文件中修改，不需要新建任何代码文件  │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

**🚫 严禁投机取巧（必须严格遵守）**：

| 禁止行为 | 说明 | 后果 |
|---------|------|------|
| ❌ 创建简化版代码 | 如 `问题一_简化版.py`、`问题一_v2.py` | 逃避问题，无法真正解决 |
| ❌ 创建备选版代码 | 如 `问题一_备选.py`、`问题一_简化.py` | 代码混乱，难以维护 |
| ❌ 降低问题难度 | 简化约束、减少变量来逃避复杂计算 | 结果不符合题目要求 |
| ❌ 更换算法逃避 | 因原算法报错而换成不合适的简单算法 | 违背建模手的设计思路 |

**正确做法**：

| 正确行为 | 说明 |
|---------|------|
| ✅ 直接修改原文件 | 在 `问题一.py` 中直接修正错误 |
| ✅ 分析错误原因 | 仔细阅读错误信息，定位问题所在 |
| ✅ 逐项排查 | 检查语法、逻辑、参数、数据格式等 |
| ✅ 保持算法完整 | 不因报错而简化或更换建模手指定的算法 |
| ✅ 耐心调试 | 复杂问题可能需要多次迭代修正 |

**错误修正示例**：

```
❌ 错误做法（投机取巧）：
运行 问题一.py → 报错 → 创建 问题一_简化版.py（简化了算法）→ 运行成功但结果错误

✅ 正确做法（认真解决）：
运行 问题一.py → 报错 → 分析错误原因 → 直接修改 问题一.py → 重新运行 → 
仍有问题 → 继续分析 → 再次修改 问题一.py → 运行成功且结果正确
```

**代码运行要求**：

| 步骤 | 要求 | 说明 |
|------|------|------|
| **运行代码** | 写完代码后必须运行 | 不能只写代码不运行 |
| **检查报错** | 运行后检查是否有错误 | 包括语法错误、运行时错误 |
| **修正错误** | 直接在原文件中修改 | 禁止新建代码文件 |
| **验证结果** | 判断结果是否正确 | 结合题目要求和建模分析 |
| **丰富图表** | 确保有足够的可视化输出 | 每个问题至少1-2张图表 |

**图表丰富性要求**：

- 每个问题的代码运行后必须生成**丰富的可视化图表**
- 图表类型应多样化，包括但不限于：
  - 折线图、柱状图、散点图
  - 热力图、箱线图、饼图
  - 3D图、等高线图
  - 网络图、树状图（根据问题类型）
- 图表应清晰展示关键结果和发现
- 所有图表保存为SVG矢量格式到 `figures/` 目录（LaTeX直接引用，无限缩放不失真）（矢量图，可无损缩放）

### 第四步：结果验证

**每道题代码运行后必须进行结果验证**：

1. **确保结果输出**：每道题的代码运行后必须有合理的结果输出
   - 输出到 `.csv` 文件：表格形式的数据结果
   - 输出到 `.txt` 文件：详细的计算过程和结果说明
   - 输出到终端：关键结果的打印显示

2. **判断结果正确性**：
   - 结合题目要求：检查结果是否满足题目中的约束条件和目标
   - 结合建模分析文档：验证结果是否符合建模手的预期
   - 结合运行效果：检查可视化图表是否合理、数据是否异常

**验证检查清单**：

| 检查项 | 说明 |
|-------|------|
| 结果完整性 | 所有要求的输出项都已生成 |
| 结果合理性 | 数值范围、符号、量级是否符合预期 |
| 约束满足 | 是否满足题目中的约束条件 |
| 图表验证 | 可视化结果是否直观、合理 |

### 第四步补充：ARIS 实现质量审计准备

验证通过后，在提交审稿手审计之前，编程手需完成以下三项自检准备：

#### A. Code-Audit 自检（ARIS 模块 2.1）

| # | 检查项 | 方法 |
|---|--------|------|
| 1 | 约束可行性 | 逐条验证优化结果是否满足所有约束 |
| 2 | 求解器交叉验证 | 如有多个 solver，结果是否一致（误差 < 1%） |
| 3 | 死代码检测 | 是否有定义了但从未调用的函数 |
| 4 | 结果文件溯源 | results/ 中的每个文件是否由 solver 真实生成 |

自检通过后，审稿手进行正式 code-audit，产出 `sessions/{name}/assurance/code_audit.json`。

#### B. Result-to-Claim 映射（ARIS 模块 2.2）

对每道题构建"结果→论断"映射表：

```markdown
## 问题N 结果支撑表
| 论文论断 | 来源 Solver | 结果文件 | 数值 | 支撑程度 |
|---------|------------|---------|------|---------|
| 最优成本 1256.3万 | problem1_lp.py | results/cost.csv | 1256.3 | supported |
```

产出 `sessions/{name}/assurance/claim_map.md`（coder 起草内容，审稿手在 Gate 2 审查验证）。

#### C. Sensitivity-Audit 自检（ARIS 模块 2.3）

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 关键参数数量 | ≥ 3 个 |
| 2 | 扰动幅度 | ±20% 基准 |
| 3 | 量化变化 | 必须有 % 数值，"显著变化"不通过 |
| 4 | 最敏感参数 | 明确标识并讨论实际含义 |

产出 `sessions/{name}/assurance/sensitivity_audit.json`。

**自检全部通过后**，进入审稿手 Gate 2。审稿手是独立批判角色（见 `roles/审稿手.md`），FAIL 的项由编程手修复后重新提交审计。

### 第五步：迭代改进

**如果结果不正确，必须先改进代码再进行下一个问题**：

```
┌────────────────────────────────────────────────────────────┐
│  编程手问题解决流程                                        │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  问题1: 编写代码 → 运行 → 结果验证                          │
│      ├─ 结果正确 → 继续问题2                               │
│      └─ 结果错误 → 改进代码 → 重新运行 → 重新验证           │
│                                                            │
│  问题2: 编写代码 → 运行 → 结果验证                          │
│      ├─ 结果正确 → 继续问题3                               │
│      └─ 结果错误 → 改进代码 → 重新运行 → 重新验证           │
│                                                            │
│  ... 以此类推，直到所有问题都正确解决                       │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

**迭代改进原则**：

| 原则 | 说明 |
|------|------|
| **问题隔离** | 每次只解决一个问题，确保当前问题正确后再进入下一个 |
| **代码调试** | 检查算法实现、参数设置、数据处理逻辑 |
| **结果对比** | 对比改进前后的结果，分析变化原因 |
| **文档记录** | 记录每次改进的内容和原因 |

## 代码要求

### 0. 核心原则（必须严格遵守）

**⚠️ 编程语言确认（第一条，必须最先执行）**：
- 在编写任何代码之前，必须先向用户确认使用的编程语言
- 如果用户未指定，必须主动询问：Python 或 MATLAB
- **禁止**在未确认编程语言的情况下直接开始编写代码
- 只有在明确用户指定的编程语言后，才能开始代码编写

**遵循建模手的设计**：
- **严格按照建模手的思路**：必须完全按照建模手在分析文档中设计的思路进行代码编写
- **严格使用指定的模型和算法**：必须使用建模手选择的数学模型和算法，不得自行更换
- **保持一致性**：代码实现应与建模分析文档保持完全一致

**超时处理原则**：
- 当代码运行超时时，**加长等待时间**，不要重新写简化的代码
- 超时通常是由于计算复杂度或数据量大导致的正常现象
- 可以通过调整超时参数、使用更高效的实现方式、增加计算资源等方式处理
- 保持算法和模型的完整性，不要为了速度而简化算法
